# Claude Code ネイティブ構成要素の書式（正確版）

> フェーズ 0・3 で読む。生成物が Claude Code に正しく認識されるための**書式の正本**。
> ここを外すと skill が起動しない／agent が編集してしまう等が起きる。

## 構成要素の一覧

| 構成要素 | 配置 | 役割（このチームでの対応） |
|---|---|---|
| ルート `CLAUDE.md` | プロジェクト直下 | オーケストレーター（司令塔）＋プロジェクト全体方針。常に読まれる |
| 部門 `CLAUDE.md` | `<領域>/CLAUDE.md` | 領域固有コンテキスト（近い方が優先）。**領域の数だけ必ず置く** |
| 共通ルール | `.claude/rules/*.md` | 全員が従う規範。**自動では読まれない。ルート CLAUDE.md から明示的に読ませて初めて効く** |
| ルーティング表 | `.claude/rules/organization.md` | キーワード→担当の SoT |
| 専門ペルソナ | `.claude/skills/<role>/SKILL.md` | 各機能領域の実作業（Skill ツールで起動） |
| 閲覧専用レビュアー | `.claude/agents/<name>.md` | 横断レビュー（read-only サブエージェント） |
| スラッシュコマンド | `.claude/commands/<name>.md` | 頻出作業のショートカット（`/<name>`） |

## 1. ペルソナ skill の書式

`.claude/skills/<role>/SKILL.md`。`<role>` は kebab-case。

```markdown
---
name: <role>
description: <領域>の<肩書き>担当（<担当名>）。【主担当】<責任を持つ実作業>。【召集】「<キーワード1>」「<キーワード2>」…。【境界線】<作業X>は<別担当>／<作業Y>は<別担当>。<リスク文脈なら>＜レビュアー＞と必ず併用召集。
---

# <肩書き>

> **担当者名**: <担当名>

## 部門 / 役割
## 担当業務（箇条書き）
## 作業ディレクトリ
## 必須読み込み（参照ルール・部門 CLAUDE.md へのリンク）
## 進め方
## やらないこと（スコープ外と引き継ぎ先）
```

**description が triggering の生命線**。コツ：
- 【主担当】【召集】【境界線】の 3 ブロックを必ず入れる。`description` は起動判定にそのまま使われるため、ここが薄いと呼ばれない。
- 【召集】には**人間が実際に使う言葉**（社内用語・略語・成果物名）を具体的に並べる。
- 少し“押し”を持たせる（「〜に少しでも触れる依頼には必ずこのスキルを使う」等）。Claude は skill を**過小起動**しがちなため。
- 【境界線】を必ず書く。これが無いと担当が被って振り分けが揺れる。

## 2. 閲覧専用レビュアー agent の書式

`.claude/agents/<name>.md`。**編集できないツール構成が肝**。

```markdown
---
name: <name>
description: 横断サポートの<領域>レビュアー（<担当名>）の閲覧専用レビュー agent。<何を/どの観点でチェックするか>。対象物は編集せず指摘のみ返す。<どの成果物の公開/実行前に>オーケストレーターが Task 起動する。<対象外>。
tools: Read, Grep, Glob
model: inherit
---

あなたは **<担当名>**。<領域>の **閲覧専用レビュアー** です。

## 起動時にまず読む（知識の正本 = SoT）
1. <チェック観点の正本となるファイル>
2. <ルール本体>

## やること
- プロンプトで渡された対象をレビューする
- **ファイルは絶対に編集しない**（使えるのは Read / Grep / Glob のみ）。修正は呼び出し元が反映する
- 曖昧な場合は厳しめに判断

## 対象外
- <レビュー不要な範囲。過剰召集を防ぐ>

## 報告（最終メッセージにまとめて返す）
- 指摘リスト（該当箇所 / 理由 / 根拠）
- 改善案（複数案）
- 判定: ✅ / ⚠️ / ❌
- 呼び出し元への申し送り（優先順位つき）
```

ポイント：
- `tools: Read, Grep, Glob` に限定すると**構造的に編集不可**になる。「編集しないでください」と本文で頼むのではなく、ツールの側で封じる。
- `model: inherit` で親セッションのモデルを継承。
- レビュアーは general-purpose ではなく**この agent 名を直接 `Task(subagent_type="<name>")` で起動**する。
- producer（ペルソナ）の内側からは agent を起動できない。**オーケストレーター（メインスレッド）が producer 実行後にレビュアーを起動**する。

## 3. ルート CLAUDE.md（オーケストレーター）

プロジェクト直下。常に読まれる。役割：

- 担当者一覧と振り分け手順（解析 → 1 行宣言 → 起動 → レビュアー召集 → 統合報告）
- 共通ルール（`.claude/rules/`）へのリンクと、**「作業前に必ず読む」という明示の指示**
  （リンクを並べるだけでは読まれない。`rules/` は自動で適用される仕組みではない）
- ルーティングの詳細は `.claude/rules/organization.md` に外出し（SoT）

## 4. ルーティング表 organization.md（SoT）

`.claude/rules/organization.md`。キーワード→領域→担当の対応表を**1 ファイルに集約**。他ファイルと矛盾したらこれを優先と明記する。

## 5. スラッシュコマンド

`.claude/commands/<name>.md`。frontmatter は `description:` のみで十分（必要なら `argument-hint`, `allowed-tools`）。本文末に `$ARGUMENTS` を置くとユーザー入力が差し込まれる。

```markdown
---
description: <このコマンドが何をするか1行>
---

<やること>

## 手順
1. …

## ユーザー入力
$ARGUMENTS
```

## 6. 連携パターン（methodology の Claude Code 実装）

- **並列**（独立業務）：1 メッセージ内に複数 `Task` を並べて同時起動。
- **直列**（前工程→後工程）：ペルソナを順に起動。
- **主担当＋レビュアー**：オーケストレーターが producer を実行 → 戻り値を受けてレビュアー agent を起動。
- **複数レビュー**：該当 reviewer agent を同一メッセージで並列 Task 起動。

## 7. よくある落とし穴

- skill が起動しない → description が抽象的すぎる。具体キーワード＋押しを足す。
- 生成したのに skill / command が一覧に出ない → セッションを開き直していない。作った直後のセッションでは認識されない。
- 書いたルールが効かない → ルート CLAUDE.md に読み込みの指示が無い。リンクを置いただけになっている。
- reviewer が編集してしまう → `tools` 行が広すぎる。`Read, Grep, Glob` に絞る。
- 振り分けが揺れる → 【境界線】不足、または organization.md とペルソナ description の不整合。
- 既存 `.claude/` を破壊 → 上書きしない。差分追加か別ディレクトリに。
