# 組織モデル方法論

> Claude Code 上で「エージェントのチーム」を組むための、**業種非依存の設計パターン**。フェーズ2（組織設計）で読む。
> ここに書くのは **構造** だけ。例に出てくる業種・役職名は型を示すための仮の言葉であり、
> **生成するチームには持ち込まない**（中身はヒアリングで聞いた言葉だけで作る）。

## 1. 3層構造

すべてのチームはこの3層で構成する。

```
プリンシパル（人間 = 経営者/依頼者）
    ↓ 指示
オーケストレーター（司令塔 / 1体）
    ↓ 振り分け
専門ペルソナ（主担当 N体） ＋ 横断レビュアー（ゲート役 M体）
```

| 層 | 役割 | 数 |
|---|---|---|
| プリンシパル | 指示・優先順位・最終承認。エージェントではなく人間 | 1 |
| オーケストレーター | 指示を解析 → 担当を特定 → 宣言 → 起動 → 成果を統合して報告 | 1 |
| 専門ペルソナ | 各機能領域の実作業 | 4〜8（まずは少なく） |
| 横断レビュアー | リスク領域のチェック（指摘のみ・編集しない） | 0〜4 |

**なぜこの形か**：単一の万能エージェントより、(a) 役割が明確で各エージェントの文脈が短く保てる、(b) 振り分けの判断が説明可能になる、(c) リスクチェックを独立したゲートに分離できる、ため。

## 2. オーケストレーター（司令塔）

依頼の入口。ルート `CLAUDE.md` がこの役を担う。設計要件：

1. **解析**：依頼文からルーティング表で担当を特定する。
2. **宣言（1行）**：作業前に「**◯◯領域の △△（担当名）として作業します**」と宣言する。これにより人間が振り分けの妥当性を即チェックできる。
3. **起動**：該当ペルソナ定義 → 部門コンテキスト → 共通ルールの順で読み込む。
4. **連携指揮**：複数領域にまたがる依頼は、並列／直列で担当を動かす。
5. **レビュアー召集**：リスク要件に該当したら横断レビュアーを併用する。
6. **統合報告**：何をしたか / 担当 / ルール準拠 / 次アクション をまとめて人間に返す。
7. **不明時は止まる**：振り分け先が複数候補・不明・機微情報を伴うときは**勝手に推測せず人間に確認**する。

## 3. ルーティング表（チームの唯一の正本 / SoT）

オーケストレーターの判断基盤。**キーワード/文脈 → 領域 → 主担当 → 作業ディレクトリ** の対応表。

| キーワード/文脈 | 領域 | 主担当 | 作業ディレクトリ |
|---|---|---|---|
| （業務に固有の語） | （部門） | （ペルソナ名） | （パス） |

設計の勘所：
- **1指示につき主担当を1名特定できる**粒度にする。
- キーワードは「人間が実際に使う言葉」で書く（社内用語・略語・商品名など）。
- 表に載らない依頼が来たら「不明 → 人間に確認」へ落とす行を必ず用意する。
- **作業ディレクトリ列は実在するパスだけを書く。** 表を書いたら、その場でディレクトリを掘る。
- この表が散らばると振り分けが壊れる。**1ファイルに集約**し、他の記述と矛盾したらこの表を優先と明記する。

## 4. 専門ペルソナ（主担当）の書式

各ペルソナは必ず次の4要素を持つ。これが揃っていないとオーケストレーターが振り分けられない。

1. **役割（主担当）**：この人が責任を持つ実作業。
2. **召集トリガー**：どんなキーワード/文脈で呼ばれるか。
3. **境界線**：「これは別の誰々の担当」を明示。**最重要**。これが無いと担当が被って揺れる。
4. **参照ルール**：作業時に必ず従う共通ルール。

設計の勘所：
- **まず4〜8体**。多すぎると振り分けが難しくなる。1人に複数機能を兼務させてよい（例：経理と総務を1名に集約）。
- 事業が複数ブランド/チャネルを持つ場合、ペルソナを「ブランド別」ではなく「**機能別**（マーケ/制作/分析/経理…）」で切り、ブランド差はルール層やコンテキストで吸収する方が破綻しにくい。
- 兼務の線引きも「境界線」に書く。
- **領域とディレクトリは1対1**。ペルソナの作業場所が、その領域のディレクトリになる。

## 5. 横断レビュアー（ゲート役）

特定領域のリスクを公開/実行前にチェックする独立エージェント。

**設計の鉄則**：

- **指摘のみ・編集禁止**。レビュアーは対象を直さず「指摘＋改善案」だけ返す。修正は producer かオーケストレーターが反映する。閲覧専用ツール（`Read, Grep, Glob`）に限定して、構造的に編集できないようにする。
- **並列起動**：複数レビュー（例：法務＋個人情報）は同時に走らせる。
- **召集条件を明記**：どの成果物のときに誰を呼ぶか（例：消費者向けコピー → 法務レビュー、個人情報を含む公開物 → 個人情報＋セキュリティを並列）。
- **対象外も書く**：レビュー不要な範囲（例：社内向けの数値レポートは法務レビュー対象外）を明記して過剰召集を防ぐ。

レビュアーを何種類置くかは業務のリスク源次第。リスクが軽い業務なら0でもよい。
業種ごとの典型：広告表現の規制がある業種なら法務、顧客データを扱うなら個人情報、
公開システムを持つならセキュリティ、ブランドの見え方が売上に直結するならデザイン整合。

## 6. 共通ルール層

全エージェントが常に従う規範。`.claude/rules/*.md` に1ルール1ファイルで置く。

- **自動では読まれない。** `.claude/rules/` は Claude Code の組み込みの仕組みではなく、ただの Markdown 置き場。
  **ルート `CLAUDE.md` から明示的にリンクし、「作業前に必ず読む」と書いて初めて効く。**
- **「具体は一般に勝つ」**：個別業務のルールが共通ルールと衝突したら個別を優先、と明記する。
- 典型カテゴリ：①ブランド/トーン（声・配色・禁止表現）②コンプラ/法務（業界の規制）③データ取扱（機微度・マスキング・保存期間）④命名/出力形式 ⑤承認フロー。
- 業務に無いカテゴリは作らない（規制の無い業種にコンプラルールは要らない）。
- **常時読み込むものを増やすと毎回のコストになる。** 1回しか使わない知識はルールでなく成果物ファイルに置く。

## 7. 階層コンテキスト

文脈を3層で重ねる。近いファイルほど具体的で優先される。

```
ルート司令塔（全体方針・ルーティング・共通ルールへのリンク）
   └ 部門/領域コンテキスト（その領域固有の方針）
        └ タスク/案件コンテキスト（個別案件の仕様）
```

エージェントは「ルート → 部門 → タスク」の順に読み、後勝ち（具体が一般に勝つ）で解釈する。

**部門コンテキストは領域の数だけ必ず作る。** 領域を切ったのに置き場所が無いと、
その領域の前提が全部ルートに集まってきて、関係ない依頼のときにも読まれることになる。

## 8. 承認ゲート（人間チェックポイント）

不可逆・外部公開・高リスクな工程には、人間の明示承認を挟む。
典型的な停止点：外部への送信・公開、発注・支払い、本番反映、顧客データの持ち出し。

設計要件：
- **停止点を定義**：どの工程完了時に止まるか、成果物は何か、人間が何を確認するか。
- **承認語を定義**：「OK」「進めて」等、人間の明示 GO が出るまで次工程に着手しない。
- **修正ループ**：差し戻しは同じ停止点に戻って再実行 → 再承認。
- **バイパス条件**：人間が「一気にやって」等と明示したスコープに限り省略可。既定は常に停止点ありにする。

工程が長い場合は途中にも停止点を置く。例えば「下書き → 音声/画像 → 公開」のような
生成物が段階的に育つパイプラインは、段ごとに承認を挟むと手戻りが小さくなる。

承認ゲートは全業務に必須ではない。**不可逆/外部公開/コストの大きい工程がある業務にだけ**設ける。

## 9. 設計順序のまとめ

1. リスク源と承認が要る工程を洗い出す（→ レビュアーとゲートの要否が決まる）
2. 機能領域を4〜8に割る（→ ペルソナとディレクトリ）
3. 兼務と境界線を決める
4. キーワード → 担当 → ディレクトリのルーティング表を書く
5. 全員が従う共通ルールを3〜5本に絞る
6. 階層コンテキストに落とす（部門ディレクトリと部門 CLAUDE.md を領域の数だけ作る）
7. 頻出作業をワークフロー化する
