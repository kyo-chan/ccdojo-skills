# Team Setup — 業務に合わせたチームを作る

Claude Code の上に、**その業務に最適化したエージェントのチームをゼロから設計・生成する**ためのスキル。

Claude Code はサブエージェント・Skill・スラッシュコマンド・階層 CLAUDE.md・ツール制限をネイティブに持つ。
それらを組み合わせて、**司令塔が依頼を受けて担当へ振り分ける**形の組織をそのまま作れる。

## 完了の定義

次がすべて揃った時点で完了とする。**どれか1つでも欠けていたら未完**。

1. `.claude/rules/organization.md`（ルーティング表）がある
2. **領域ごとにディレクトリが実在し、その中に部門 `CLAUDE.md` がある**
3. ルーティング表の「主な作業ディレクトリ」列のパスが、1つ残らず実在する
4. 領域ごとの専門ペルソナ skill がある
5. リスク源があるなら、閲覧専用レビュアー agent がある
6. ルート `CLAUDE.md`（司令塔）がある
7. 生成物に `{{` と `<!--` が1つも残っていない

## 最重要原則：作るのは、聞いた言葉だけでできたチーム

このスキルの説明文・テンプレートの例文は、**あくまで型を示すための仮の言葉**。
生成物にそれが残っていたら、それは置換漏れであってユーザーのチームではない。

> **検査軸：生成物に出てくる固有名詞は、すべてフェーズ1のヒアリングでユーザー本人が口にした言葉か。**

領域名・担当名・キーワード・ルール・ディレクトリ名——どれも、聞いていないものを埋めない。
埋まっていない項目があるなら、設計に進まずに聞く。

## 進め方（4フェーズ）

このスキルは対話型。下記4フェーズを順に進める。各フェーズの詳細は references を必要時に読む。

### フェーズ0：前提合わせ

1. 生成先プロジェクトのパスを確認する（その直下に `.claude/` と `CLAUDE.md` を作る）。既存プロジェクトに足すのか、新規かを確認。
2. `references/claude-code-constructs.md` を読み、各構成要素（CLAUDE.md / skills / agents / rules / commands）の**正確な書式（frontmatter）**を把握する。
3. **既存の中身を見る。**
   - 既存 `.claude/` がある場合は**上書きしない**。差分追加か、別ディレクトリ生成かをユーザーに確認する。
   - 既存のフォルダ構成があれば、**部門ディレクトリの命名をそれに合わせる**（下記）。

#### 部門ディレクトリの命名

既定は **`NN_領域名/`**（`01_制作/` `02_マーケ/` …）。番号を振ると一覧の並びが固定され、
あとから領域を足したときの順序も残る。

既存のフォルダ構成があるなら、そちらの呼び方に合わせる。
どちらにするかはフェーズ2の設計案に含めてユーザーの承認を取り、確定したら `.claude/rules/naming.md` にも書く。

### フェーズ1：業務ヒアリング（最重要）

チームの質はここで決まる。`references/interview-guide.md` を読み、その質問セットで業務をヒアリングする。

- 一度に全部聞かず、`AskUserQuestion` などで**塊ごとに**聞く。すでに分かっている項目は飛ばす。
- 最低限：①業種・事業構造 ②機能領域（部門・職能）③繰り返し発生する具体タスク ④コンプラ/法務/品質などの**ゲート要件** ⑤誰が何を承認するか ⑥扱うデータの機微度 ⑦使う外部サービス/MCP（レビュアーのツール制限やコマンド設計に効く）。
- 不明点を埋めずに設計に進まない。

### フェーズ2：組織設計（人間の承認を取る）

`references/methodology.md` の組織パターンに沿って、ヒアリング結果から次を**設計案として提示し承認を得る**。生成は承認後。

1. **オーケストレーター**（司令塔 / ルート `CLAUDE.md`）：依頼解析 → 担当特定 → 1行宣言 → 起動 → 統合報告。
2. **機能領域とディレクトリ**：領域を4〜8に割り、それぞれのディレクトリ名を決める。**領域とディレクトリは1対1**。
3. **専門ペルソナ**（`.claude/skills/<role>/SKILL.md`）：領域ごとに1体。各々「役割 / 召集 / 境界線 / 参照ルール」。
4. **閲覧専用レビュアー**（`.claude/agents/<name>.md`）：リスク源に応じて0〜4体。**`tools: Read, Grep, Glob` に限定して構造的に編集不可**にする。
5. **共通ルール層**（`.claude/rules/*.md`）：全員が従う。「具体は一般に勝つ」。
6. **ルーティング表（SoT）**：`.claude/rules/organization.md` にキーワード→領域→担当→ディレクトリを集約。
7. **スラッシュコマンド**（`.claude/commands/*.md`）：頻出作業のショートカット。
8. **承認ゲート**：不可逆・外部公開・高リスク工程に人間承認チェックポイント。

設計案は「組織図（テキスト）＋ルーティング表ドラフト＋ディレクトリ構成」で見せると合意が速い。

#### 命名（必ずユーザーに確認する）

チームの「らしさ」と振り分けの分かりやすさは名前で決まる。**オーケストレーター・各専門ペルソナ・各レビュアーのすべてに名前をつける。**

- 役割が固まったら、各担当の名前を **`AskUserQuestion` でユーザーに確認する**。勝手に確定しない。
- ユーザーが「任せる」と言ったら、役割・業務・トーンに合った候補を提案し、承認を得てから確定する。
- 人名で統一するか役職名で統一するかを先に決め、言語（和名/英名）やトーンを業務に合わせて揃える。
- 確定した名前は **ルーティング表・各 `SKILL.md`/`agent.md` の `description`・宣言フォーマット（「◯◯領域の △△（`<skill-name>`）として作業します」）すべてに反映する。**
- テンプレートの `{{担当名}}` プレースホルダは、ここで確定した名前で必ず置換する。

### フェーズ3：ファイル生成

承認後、`assets/templates/` を土台にヒアリング内容を流し込んで生成する。

**着手前に、生成物リストを確定してユーザーに見せる。**「何を何本作るか」を先に固定し、走りながら数を増やさない。

```
これから作るもの（全 N 本）
- ルーティング表 1
- 部門ディレクトリ 5 ＋ 部門 CLAUDE.md 5
- ペルソナ skill 5
- レビュアー agent 2
- 共通ルール 3
- ルート CLAUDE.md 1
- スラッシュコマンド 2
```

#### 生成順（この順を崩さない）

1. `.claude/rules/organization.md`（ルーティング表）— **領域・担当・ディレクトリパスをここで確定する**
2. **部門ディレクトリを作る** — 表の「主な作業ディレクトリ」列のパスをそのまま掘る
3. 各ディレクトリに**部門 `CLAUDE.md`**
4. ペルソナ skill（領域ごとに1本）
5. レビュアー agent
6. `.claude/rules/*.md`（共通ルール）
7. ルート `CLAUDE.md`
8. `.claude/commands/*.md`

ルーティング表を最初に確定させると、以降のファイルの `description`・境界線・パスがすべてそこから引ける。
表とディレクトリを2番目でそろえておくと、後続の生成物が実在しないパスを指す事故が起きない。

書いたファイルは**その場でリストに印を付ける**。全部書き終えてからまとめて検算しない。
中断しても、ルーティング表の各行に対して「ディレクトリ有無 / 部門 CLAUDE.md 有無 / skill 有無」を見れば再開点が分かる。

#### 出力構成

```
<生成先プロジェクト>/
├── CLAUDE.md                       # ルート司令塔（オーケストレーター）
├── .claude/
│   ├── rules/
│   │   ├── organization.md         # ルーティング表（SoT）
│   │   ├── naming.md               # 命名・出力形式
│   │   ├── {{brand-or-voice}}.md
│   │   └── {{compliance}}.md       # ゲート要件があれば
│   ├── skills/
│   │   ├── {{persona-1}}/SKILL.md
│   │   └── {{persona-2}}/SKILL.md
│   ├── agents/
│   │   └── {{reviewer-1}}.md       # tools: Read, Grep, Glob
│   └── commands/
│       └── {{command-1}}.md
├── {{01_領域A}}/CLAUDE.md          # 領域の数だけ必ず作る
├── {{02_領域B}}/CLAUDE.md
└── {{03_領域C}}/CLAUDE.md
```

| 生成物 | テンプレート |
|---|---|
| ルート司令塔 | `assets/templates/root-CLAUDE.md` |
| 部門コンテキスト | `assets/templates/department-CLAUDE.md` |
| ルーティング表（SoT） | `assets/templates/organization.md` |
| 専門ペルソナ skill | `assets/templates/persona-SKILL.md` |
| 閲覧専用レビュアー agent | `assets/templates/reviewer-agent.md` |
| 共通ルール1本 | `assets/templates/rule.md` |
| スラッシュコマンド | `assets/templates/command.md` |

> テンプレート冒頭の `<!-- ... -->` は使い方の注記。**生成物には残さず削除する。**
> `{{...}}` は必ず実値に置換する。
> frontmatter の正確な書式は `references/claude-code-constructs.md` を参照（特に agent の `tools` 行、skill の `name`/`description`）。

### フェーズ4：検証

機械で当てられるものは機械で当てる。

```bash
cd <生成先>

# 置換漏れ・注記の消し忘れ（どちらも0件になること）
grep -rn "{{" . --include="*.md"
grep -rn "<!--" . --include="*.md"

# レビュアーが編集できない構成になっているか
grep -n "^tools:" .claude/agents/*.md
```

- **領域数 ＝ 部門ディレクトリ数 ＝ 部門 `CLAUDE.md` の数**。3つが一致しなければ未完
- ルーティング表の「主な作業ディレクトリ」列のパスを1行ずつ `ls` で当て、**全部実在する**こと
- **新しいセッションを開き直してから**、skill 一覧にペルソナが、`/` にコマンドが出ることを確認する（開き直さないと認識されない）
- **振り分けテスト**：ルーティング表の各行から依頼文を1件ずつ作り、宣言される担当が表と一致するか
- **レビュアーテスト**：レビュー対象を渡し、指摘だけが返り、**対象ファイルの更新時刻が変わっていない**こと
- **承認ゲートテスト**：承認が要る工程で、人間の GO 無しに次工程へ進まないこと

## よくある失敗と対処

- **ペルソナを盛りすぎる** → まず4〜8体。1人に複数機能を兼務させてよい。
- **境界線が曖昧で振り分けが揺れる** → 各ペルソナ description の【境界線】を必ず書く。
- **レビュアーが編集してしまう** → agent の frontmatter を必ず `tools: Read, Grep, Glob` に。本文にも「編集禁止・指摘のみ」を明記。
- **description が弱くて skill が起動しない** → 【主担当】【召集】【境界線】を具体キーワードで埋め、少し押しを持たせる（`claude-code-constructs.md` 参照）。
- **書いたルールが効かない** → `.claude/rules/` は自動では読まれない。ルート `CLAUDE.md` に「作業前に必ず読む」と書いて初めて効く。
- **ルーティング表のパスが実在しない** → 部門ディレクトリを作る前にペルソナを書いた。生成順を守る。
- **既存 `.claude/` を壊す** → 上書きしない。差分追加か別ディレクトリ生成かを必ず確認。

- `references/claude-code-constructs.md` — Claude Code ネイティブ構成要素の正確な書式と設計の勘所。フェーズ0・3で読む。
